# Red-team evidence register

## Purpose and authority boundary

This register records adversarial checks against IN KEEPING and links each reproduced failure to its constraint, correction, executable evidence, and remaining limit. It supplements the candidate-specific [`VALIDATION_REPORT.md`](VALIDATION_REPORT.md); it is not a certification, penetration-test attestation, institutional acceptance, or claim that every attack class has been exhausted.

The defining question is:

> Can IN KEEPING produce an artifact that looks complete, authoritative, and internally consistent when its evidence is incomplete, altered, ambiguously identified, or unrecoverable?

The governing answer remains: **integrity is not authenticity**. Internal hashes can expose inconsistency in the content presented to the validator. They do not establish that the original content was true or complete, identify an actor, prove custody or authorization, supply trusted time, or prevent a capable party from replacing and rehashing an entire history.

Status terms are deliberately narrow:

- **Failed:** the attack produced an unsafe or misleading result before correction.
- **Corrected:** implementation and regression evidence exist in this working tree.
- **Focused verified:** the named regression path passed during this run; this is not the complete engineering suite or release gate.
- **Open:** no sufficient application control has been established.
- **External:** the required evidence or control cannot be supplied by this repository alone.
- **Pending:** the named check or drill has not yet been recorded as complete.
