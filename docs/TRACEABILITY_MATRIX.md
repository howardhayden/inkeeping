# Requirements traceability matrix

## How to read this matrix

This matrix links product/security requirements to implementation, evidence artifacts, and validation responsibilities. It distinguishes four evidence classes:

- **A — automated:** an executable test asserts the behavior. A test file's existence does not mean the current candidate passed; consult [`VALIDATION_REPORT.md`](VALIDATION_REPORT.md).
- **I — implementation inspection:** the behavior is directly visible in source/configuration, but automated evidence is absent or incomplete.
- **M — manual:** a human interaction, visual, workflow, or document review is required.
- **E — external:** evidence comes from the live host, institution, vendor/product, account, or policy system outside this repository.

Status terms:

- **Implemented:** source contains the control and named automated evidence exists.
- **Implemented; inspection only:** source contains the control but a dedicated executable assertion is not identified.
- **Design target; manual evidence pending:** implementation support exists, but the quality claim cannot be made without manual results.
- **External acceptance required:** repository code cannot establish the requirement.

## Evidence gaps and required actions

| Gap | Required action | Release effect |
| --- | --- | --- |
| Focus/keyboard/draft/status contracts are primarily source-pattern tests. | Execute and record browser interaction and assistive-technology protocols. | Blocks accessibility conformance or production accessibility acceptance. |
| Source/configuration cannot prove live headers or absence of unexpected platform/network behavior. | Capture canonical-origin response headers and browser network activity after deployment. | Blocks production acceptance. |
| Repository tests cannot establish vendor-profile interoperability. | Import/export representative institutional fixtures with named product versions/configurations. | Blocks workflow reliance for each unvalidated exchange path. |
| Wrangler observability setting cannot establish all Cloudflare account logging/analytics behavior. | Complete platform privacy/security review and retain account evidence. | Blocks institutional privacy approval. |
| Focused test results in the current validation report are not a full immutable release result. | Run `npm run release:check` on the release commit and complete the acceptance record. | Blocks release. |

## Change-control rule

Every pull request that changes a requirement or its implementation must update the corresponding row. A row cannot move to “Implemented” solely because documentation was added. It requires code plus executable evidence, or an explicit inspection/manual/external classification where automation cannot establish the claim.
